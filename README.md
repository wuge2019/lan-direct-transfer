# 局域网直连 · 通信与文件实时传输

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)
[![Vue 3](https://img.shields.io/badge/Vue-3-42b883.svg)](https://vuejs.org/)
[![Vite](https://img.shields.io/badge/Vite-6-646cff.svg)](https://vite.dev/)
[![TypeScript](https://img.shields.io/badge/TypeScript-5-3178c6.svg)](https://www.typescriptlang.org/)
[![No upload](https://img.shields.io/badge/%E6%96%87%E4%BB%B6-%E4%B8%8D%E7%BB%8F%E6%9C%8D%E5%8A%A1%E5%99%A8-success.svg)](#7-工作原理)

局域网内的即时通信 + 文件实时传输工具：**聊天内容与文件分片始终走 WebRTC 点对点直连，
不经过任何服务器，也不上传到第三方**。

两种使用方式，按需要选：

| 方式 | 体验 | 依赖 |
| --- | --- | --- |
| **A. 自动发现（推荐）** | 打开页面就能看到局域网里所有在线用户 → 点选 → 对方同意 → 立即建立直连 | 一台机器跑 `pnpm lan`（一个 Node 进程，无数据库） |
| **B. 纯前端单文件** | 双击 `index.html`，人工交换一次短「信令码」完成握手 | **零依赖**，不需要任何服务 |

方式 A 里的服务只做两件事：**告诉你有谁在线**、**把你俩建立直连所需的那一小段信令转给对方**。
它不接触聊天内容，也不接触文件数据（可从 [协议](#8-自动发现与信令服务) 一节逐条核对）。

技术栈：**Vue 3 + Vite + TypeScript**（Composition API、单文件组件）。

## 1. 特性

| 能力 | 说明 |
| --- | --- |
| 自动发现用户 | 局域网内谁在线一目了然，点选即可发起连接（方式 A） |
| 请求—同意 | 连接需要对方在弹窗里点「同意」，不同意绝不会连上；30 秒未处理自动拒绝 |
| 自定义昵称 | 昵称随时可改，改名后其他人的列表实时更新 |
| 点对点直连 | 聊天与文件走 WebRTC DataChannel，不经过服务器、不落任何第三方 |
| 实时聊天 | 文字消息、时间戳、连接状态、往返延迟（RTT）实时显示 |
| 文件实时传输 | 拖拽即可发送、多文件排队、进度/速度/剩余时间、可随时取消 |
| 恒定内存 | 走「询问保存位置 / 固定文件夹」时两端内存恒定，几个 GB 的文件也不会撑爆内存 |
| 完整性校验 | 传输过程中增量计算 CRC-32，结束后双方比对，损坏立即报错 |
| 流控 | 接收端按「写完多少」回执信用额度，慢磁盘不会导致接收端内存堆积 |
| 分片流号 | 每个分片带 4 字节流号，取消后残留在途分片不会被算进下一个文件 |
| 状态收敛 | 终态不会被异步路径改写；发送端失败/取消会通知接收端停止并释放文件 |
| 断线可恢复 | 断开后重新连接即可继续发送，不需要刷新页面 |
| 扫码加入 | 服务页面直接显示局域网地址二维码，手机扫一下就能进来（方式 A） |
| 本机自测 | 同一浏览器开两个标签页，可用 `BroadcastChannel` 一键自动配对，无需复制粘贴（方式 B） |
| 局域网链路可见 | 显示 `host↔host @192.168.1.5:54321` 这样的实际链路与 RTT，便于排查问题 |

> 传输本身由 WebRTC 的 DTLS 加密保护；方式 B 下 DTLS 指纹还通过你手工传递的信令码做了带外校验。

## 2. 快速开始

### 方式 A：自动发现（推荐）

在**任意一台**机器上（Windows / macOS / Linux 都行，需要 Node 22+；服务端本身只用 Node 内置模块，
但仓库的构建与测试基线是 Node 22）：

```bash
git clone https://github.com/wuge2019/lan-direct-transfer.git
cd lan-direct-transfer
pnpm install
pnpm build
pnpm lan            # 启动发现/信令服务，默认 8080 端口，会自动打开浏览器
```

启动后终端会打印局域网地址，例如：

```
  本机访问：http://localhost:8080
  局域网访问：http://192.168.1.5:8080
```

把这行地址（或页面里「邀请他人加入」中的二维码）发给同事，他们用浏览器打开就能
**互相看见**，点对方的「连接」，对方点「同意」，即可开始聊天与传文件。

```bash
pnpm lan --port 9000 --name "会议室传输房"     # 换端口 / 换房间名
pnpm lan --no-open                            # 不自动打开浏览器
```

> 服务本身不存储任何东西，按 `Ctrl+C` 停掉即全部消失；它只服务局域网，默认拒绝陌生
> Origin 的连接（详见 [第 8 节](#8-自动发现与信令服务)）。

### 方式 B：纯前端单文件（零依赖）

到 [Releases](https://github.com/wuge2019/lan-direct-transfer/releases) 下载 `index.html`，
拷贝到两台设备（U 盘 / 共享目录 / 微信），**双击用 Chrome 或 Edge 打开**，
然后按 [3.2 手动邀请码连接](#32-手动邀请码连接无需任何服务) 交换一次信令码即可。
产物是完全内联的普通脚本（约 180 KB），`file://` 下可直接运行，不需要任何服务。

> 如果你已经用方式 A 起了服务，但更想用单文件版：打开页面的「设置」，
> 在**发现服务地址**里填 `192.168.1.5:8080`，单文件版也能用上自动发现。

### 开发模式

```bash
pnpm dev --host      # Vite 热更新；注意这个页面本身不提供发现服务
pnpm preview --host  # 预览构建产物
```

⚠️ 用 `http://` 局域网地址（而不是方式 A 的服务）打开时**不是安全上下文**，
浏览器会禁用「文件系统访问 API」，接收文件会自动退化为「内存接收 + 浏览器下载」。
方式 A 的服务同样通过 `http://局域网IP` 访问，因此也有这个限制——要流式写盘大文件，
建议直接用 Chrome/Edge 打开本机 `file://` 的单文件版，或接受内存接收（≤ 512 MB）。

## 3. 连接步骤

### 3.1 自动发现连接（需要发现服务）

1. 发起方在「局域网用户」列表里找到对方，点 **连接**；
2. 对方屏幕上弹出「**XXX 请求与你建立连接**」，点 **同意**（30 秒未处理会自动拒绝）；
3. 双方状态变为「已连接」，界面顶部显示延迟与实际链路，随后即可聊天、拖文件。

连接过程中你可以在列表里看到对端状态（空闲 / 连接中 / 已连接）；
想换人时先点 **断开** 释放会话。

### 3.2 手动邀请码连接（无需任何服务）


### 发起方（A）

1. 打开页面 → 点 **生成邀请码** → 点 **复制**；
2. 把邀请码通过任意方式发给对方（微信 / QQ / 邮件 / 共享文件夹 / 手抄都行）；
3. 对方回传「应答码」后，粘贴到第 2 步的输入框 → 点 **完成连接**。

### 接收方（B）

1. 切到 **我是接收方（B）** 标签页 → 粘贴对方发来的邀请码 → 点 **生成应答码**；
2. 点 **复制** → 把应答码发回给 A；
3. A 点「完成连接」后，双方自动建立直连。

连接成功后顶部状态变为「已连接」，并显示延迟与实际链路类型，此时即可聊天、拖文件。

### 本机自测（同一台电脑）

打开两个标签页，分别点 **本机配对（主叫）** 与 **本机配对（被叫）**，两者通过 `BroadcastChannel`
自动交换信令，无需复制粘贴。

## 4. 文件接收与保存方式

在 **设置** 里可以选择三种落盘方式：

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| 每个文件都询问保存位置 | 弹系统保存对话框，分片直接流式写入磁盘 | 推荐，大文件首选（Chrome / Edge） |
| 保存到我选定的文件夹 | 授权一次目录，之后接收的文件自动写入，重名自动加 `(1)` | 批量接收大量文件 |
| 浏览器下载 | 分片先收进内存，结束后生成 Blob 触发下载 | 兼容性最好（Firefox / Safari），超大文件慎用 |

另外可勾选 **自动接受对方发来的文件**（仅在「浏览器下载」或已选定文件夹时生效，因为其他模式需要你点一下
才能弹出系统对话框）。

> 「浏览器下载」模式会把整个文件先缓存在内存里：超过 512 MB 时程序会先弹确认框提醒，
> 并建议改用「询问保存位置 / 固定文件夹」以获得流式写盘（不会撑爆内存）。

## 7. 工作原理

```
浏览器A ──┐                                   ┌── 浏览器B
          │  ①发现：谁在线（仅昵称与状态）      │
          ├────────► server/index.mjs ◄────────┤
          │  ②信令：把 300~600 字符的短码转给对方│
          │                                   │
          └════════ ③WebRTC 点对点直连 ════════┘
                 聊天 + 文件分片（不经过服务器）
```

1. **发现与信令服务（只有方式 A 需要）**
   `server/index.mjs` 是一个零依赖的 Node 进程：托管前端页面、提供 `/api/info`、
   在 WebSocket 上维护「谁在线」的名单，并在两个浏览器之间转发建立直连所需的那一小段数据。
   它**不接触**聊天内容与文件数据，也不写任何持久化存储。

2. **握手复用的是同一套「压缩信令码」**
   浏览器生成的原始 SDP 有 1.5~3 KB。`sdp-codec.ts` 只提取建立 DataChannel 必需的信息
   （`ice-ufrag`、`ice-pwd`、DTLS 指纹、host/srflx 候选地址），压成 300~600 字符的短码。
   方式 A 下这段短码由服务转发，方式 B 下由你手工复制粘贴——**两种模式的握手逻辑完全一致**。

3. **两条数据通道**
   - `ctrl`：聊天文本、文件元信息、流控回执、心跳（JSON 字符串）
   - `data`：文件分片（16 KB 负载 + 4 字节流号头）

   两条通道是**独立的 SCTP 流**，所以 `file-done` 完全可能早于最后一个分片到达——
   接收端会把这些「提前到达的结束标记」暂存，等字节数对齐后再收尾。

4. **分片带流号（容易被忽略但很关键）**
   每个二进制分片的前 4 字节是大端流号，标识它属于哪一次传输。
   因为「取消一个传输」并不能撤回已经进入数据通道的在途分片：
   如果接收端只按「当前正在收哪个文件」来归属分片，这些残留分片就会被算进**下一个**文件，
   把新文件写坏（CRC 校验会报错，但用户看到的是「新文件莫名传坏了」）。
   有了流号，失效分片会被直接识别并丢弃。

5. **信用流控（credit）**
   发送端初始有 64 个分片（1 MB）的信用额度；接收端每**真正写入磁盘** 16 个分片回执一次。
   信用耗尽即暂停发送。这样慢磁盘不会导致数据在接收端 JS 堆里堆积。

6. **完整性校验**
   发送端边发边算增量 CRC-32，结束时把结果随 `file-done` 发出；接收端用同样方式计算并比对，
   同时校验字节数，然后把结果通过 `file-ack` 回执给发送端，任一侧失败都会在界面上明确显示。

7. **状态收敛**
   所有传输状态机都有终态守卫：`done / failed / cancelled / rejected` 一旦到达就不会被其它
   异步路径改写（例如「已断开」不会被覆盖成「已取消」）；发送端失败或取消时会显式通知接收端
   停止并释放文件句柄，避免对方永远停在「接收中」并留下半截文件。

### 单文件构建的两个坑（已在 `vite.config.ts` 里处理并断言）

1. `file://` 下浏览器会以 CORS 为由拒绝执行 `<script type="module">`，
   所以构建插件把内联脚本改成普通 `<script>`；
2. **普通脚本是同步执行的**，而 Vite 默认会把 module script 提升到 `<head>` ——
   那一刻 `<div id="app">` 还没被解析出来，Vue 会挂载失败，**双击打开就是白屏**。
   因此插件会把内联脚本移到 `</body>` 之前，并在脚本位置不对时直接让构建失败。

`tests/app.smoke.spec.ts` 里有一条用 JSDOM **忠实解析产物**（不预置挂载点）的用例守着这个行为，
避免此类问题再次发生。

## 8. 自动发现与信令服务

### 它能做什么

| 消息 | 方向 | 内容 |
| --- | --- | --- |
| `welcome` / `hello` / `hello-ok` | 双向 | 打招呼、房间名、协议版本 |
| `roster` | 服务 → 浏览器 | 在线用户列表：`{peerId, name, busy}` |
| `request` / `response` | 双向 | 「我想连你」/「同意 / 拒绝 + 原因」 |
| `signal` | 双向转发 | 握手用的短码（300~600 字符的 Base64URL 文本） |
| `session-end` | 服务 → 浏览器 | 对方离线或主动结束会话 |

### 它不能做什么

- 看不到、也拿不到你的聊天文本与文件内容——那些只走 WebRTC DataChannel；
- 不落盘、无数据库，进程退出即清空；
- 不会替你决定连接谁：每一次连接都必须对方在弹窗里点「同意」。

### 安全边界

- **默认只接受同源与本机 Origin 的 WebSocket 连接**：其他网站即使知道你的地址也无法连上来
  （浏览器会带上 `Origin`，服务端据此校验）。确实需要跨源时用 `--allow-origin <主机>` 显式放行。
- 服务只监听局域网地址；不要把它暴露到公网（本项目没有做鉴权与加密传输，设计前提就是可信局域网）。
- 连接建立后，双方的直连由 WebRTC 的 DTLS 加密保护。

## 9. 已知限制

- **方式 A 需要有人起服务**：浏览器本身无法扫描局域网（没有原始套接字、不能监听端口、
  不能 mDNS 发现），所以「自动看到谁在线」必须依赖一个发现服务；不想起服务就用方式 B 手工换码。
- **同一时间只支持 1 对 1**：一次只与一个对端连接（点「断开」后可换人）。
- **不支持中继**：双方必须在同一局域网 / 可达网络内。跨网段或复杂 NAT 场景，可在设置里勾选
  「使用公网 STUN」（需要联网），但仍然没有 TURN 中继。
- **不支持断点续传 / 分片重传**：传输中断（取消、断线、校验失败）需要重新发送该文件；
  重连后可以直接继续发新文件，但不会从上次的进度接着传。
- **内存路径不适合超大文件**：Firefox / Safari 没有文件系统访问 API，只能走「内存接收 + 浏览器下载」，
  大于 512 MB 时会先弹确认框；GB 级文件建议用 Chrome / Edge 的流式写盘模式。
- **浏览器要求**：Chrome / Edge 体验最佳（支持流式写盘）；Firefox / Safari 可用，但只能走内存接收。
- 传输期间请尽量保持页面在前台：后台标签页会被浏览器调度节流，可能明显变慢
  （程序已用 `MessageChannel` 让出主线程，避免最坏情况）。
- Windows 首次使用时，如果系统防火墙弹窗询问是否允许浏览器通信（或允许 Node 监听端口），请选择「允许」。

## 10. 常见问题

**列表里看不到别人？**

1. 确认对方也是通过**同一个服务地址**打开的页面（例如都是 `http://192.168.1.5:8080`）；
2. 看页面上「局域网用户」那一行的状态：显示「没有找到发现服务」说明页面不是由服务托管的，
   可以在设置里填服务地址，或改用方式 B 手工换码；
3. 服务端的终端会打印每次上线/离线，可以直接核对；
4. 某些企业网络做了客户端隔离（AP isolation），设备之间无法互访，此时只能换网络。

**连不上怎么办？**

1. 确认两台设备在同一局域网，且都能正常互通；
2. 检查系统防火墙是否拦截了浏览器（Windows 上首次运行通常会弹窗）；
3. 看页面底部「运行日志」：会打印 ICE 候选类型、ICE 状态、连接状态；
4. 某些企业网络会屏蔽 UDP 或做了客户端隔离（AP isolation），此时 P2P 无法建立；
5. 可以试着勾选设置里的「使用公网 STUN 服务器」再重试。


**为什么对方发的文件我只能用浏览器下载？**

说明当前页面不是安全上下文（例如用 `http://192.168.x.x` 打开），或者浏览器不支持文件系统访问 API。
改用双击 `dist/index.html`（`file://`）或 Chrome / Edge 即可获得流式写盘。

**传输大文件（几个 GB）可以吗？**

可以，只要使用「询问保存位置」或「选定文件夹」模式，内存占用是恒定的。用「浏览器下载」模式时，
文件会先完整缓存在内存里，不建议超过几百 MB。

**复制按钮没反应？**

非安全上下文下浏览器会禁用 `navigator.clipboard`，程序会自动回退到 `execCommand('copy')`；
若仍失败，请手动选中文本按 `Ctrl+C`。

## 11. 测试

```bash
pnpm test
```

覆盖内容（`pnpm test` → 9 个文件、88 个用例，全部使用真实实现而非桩）：

- `tests/crc32.spec.ts`：CRC-32 已知向量、增量与一次性计算一致性、比特翻转可检出、格式化工具
- `tests/sdp-codec.spec.ts`：SDP 解析、候选过滤（去 TCP/relay）、短码打包/解包往返、
  容忍换行与包裹文字、还原后的 SDP 可再次解析、非法输入报错
- `tests/peer.spec.ts`：信令码角色校验（把应答码当邀请码粘贴会被拦下）、
  DTLS 指纹算法随码携带与向后兼容
- `tests/server.spec.ts`：**发现/信令服务**（自写的 WebSocket 实现）——握手 101/403、
  注册与在线名单、改名广播、请求/同意/拒绝、未配对者不能转发信令、忙时拒新请求、
  离线清理、非法消息容错、`/api/info`、目录穿越防护
- `tests/discovery.spec.ts`：**发现客户端**接真实服务 —— 探测接口、名单、请求/同意、
  双向信令、改名、离线通知、断线自动重连、注册前的消息排队
- `tests/transfer.spec.ts`：端到端模拟 DataChannel —— 2.5 MB 跨信用窗口传输、多文件排队、
  拒绝、数据损坏被 CRC 检出、取消、空文件、手动接受，以及一组回归用例（这些缺陷都曾真实出现过）：
  **file-done 抢跑**、**abortAll 后仍可继续发送**、**慢盘信用耗尽时取消要立刻生效**、
  **通道未就绪时排队项必须进入终态**、**abortAll 要收敛排队项**、**终态不能被覆盖**、
  **发送端失败要通知接收端**、**超大 credit 限幅**、
  **取消后立刻发新文件不被旧的在途分片污染**
- `tests/full-stack.spec.ts`：**全链路**——发现服务 + 发现客户端 + 真实 WebRTC 协议栈：
  甲点选乙 → 乙同意 → 自动完成握手 → 真实传完 1.5 MB 并通过 CRC 校验；以及拒绝时不会建立直连
- `tests/webrtc.e2e.spec.ts`：**真实 WebRTC 协议栈端到端**（Node + libdatachannel）——
  用本项目生成的邀请码 / 应答码完成真实握手，并在真实 DataChannel 上按真实分片协议传完 1.5 MB 文件；
  另有一条负向对照：**篡改 DTLS 指纹后握手必须失败**，证明测试不是空跑。
  （若本机没有可用的 `node-datachannel` 原生二进制，该文件会自动跳过）
- `tests/app.smoke.spec.ts`：用 jsdom 挂载真实 `App.vue`（在线名单渲染、连接按钮可用性、
  设置弹窗、拖拽遮罩、输入法回车、清空逻辑），并用 JSDOM **忠实解析 `dist/index.html`**、
  执行其中的内联脚本，断言界面真的渲染出来，验证「双击即用」的单文件产物确实能启动

> 特别说明：手写 SDP 与手写 WebSocket 是本项目里最容易出错的两块
> （自往返测试只能证明自洽，不能证明合法）。因此分别补了**真实 WebRTC 协议栈**
> 与**全链路**两条端到端测试来兜底。
> 注意：`app.smoke.spec.ts` 里针对构建产物的用例需要先执行过 `pnpm build`（未构建时自动跳过）。
